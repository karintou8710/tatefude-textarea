# 素の textarea の縦書き

`writing-mode: vertical-rl` を当てた `<textarea>` が何をするか。実測した値だけ書く。

## 測った結果

10 字で折り返す縦書き。offset 50 から 1 回だけキーを打つ。

| | Blink (macOS) | WebKit (デスクトップ) |
| --- | --- | --- |
| `↓` | 50 → 60 (1 列) | 50 → **69** |
| `↑` | 50 → 40 (1 列) | 50 → **49** |
| `←` | 50 → 49 (1 字) | 50 → 49 (1 字) |
| `→` | 50 → 51 (1 字) | 50 → 51 (1 字) |
| `Home` `End` `PageDown` | 動かない | 動かない |
| 折り返し | コンテナの高さで折る | 同じ |
| `scrollLeft` | 負 (`-100` が通る) | 負 (`-100` が通る) |

- **WebKit は `↑` `↓` で列の端に飛ぶ。** 開始位置を変えても着地点が変わらない (下の表)
- 矢印の軸は **Blink も macOS では OS のキーバインド由来**。縦書きでも `←→` が字送りのまま
  (Linux / Windows の Blink は画面の向きどおりに動く)。
  **WebKit の実装の意図はこのライブラリの割り当てと同じ** (`↑↓` が字送り)
- `scrollLeft` は**両方とも負**だった。`backend/scroll.ts` の「WebKit は正」は、
  いまのデスクトップ WebKit には当てはまらない。古い Safari と iOS は未確認

## キャレットの描かれ方

`caret-color: red` を当てて、同じページを両エンジンで見た (offset 2、34px の縦書き)。

| | |
| --- | --- |
| Blink | 列幅いっぱいの横線 |
| WebKit (iOS 26.4) | 位置は合っているが、**列幅の 1/3 ほどの短い横線** |

位置は正しいので「ずれる」のではなく「**短い**」。自前で描くときは字の箱の幅いっぱいに引いている。

デスクトップの WebKit は未確認。ヘッドレスではキャレットが描かれない (Blink も同じ)。

## `↑` `↓` の着地点 (1 列 = 10 文字)

| 開始 | Blink `↓` | WebKit `↓` | Blink `↑` | WebKit `↑` |
| --- | --- | --- | --- | --- |
| 50 | 60 | **69** | 40 | **49** |
| 53 | 63 | **69** | 43 | **49** |
| 55 | 65 | **69** | 45 | **49** |
| 58 | 68 | **69** | 48 | **49** |

Blink は**列内の位置を保ったまま**隣の列へ移る。
WebKit は**開始位置に関係なく、隣の列の末尾**に飛ぶ。行内位置 (goal position) が引き継がれていない。

なお WebKit には矢印を writing mode で写す実装がある
(`editing/EditorCommand.cpp` の `logicalMoveForArrowKey`、[b/62833](https://bugs.webkit.org/show_bug.cgi?id=62833))。
そこでは「縦書きなら `↑` `↓` は字送り」と書かれているが、macOS では実測のとおり行移動になっている。
OS のキーバインドが先に効いていて、この経路を通っていないと思われる。

## iOS 26.4 (シミュレータ) で見たこと

縦書きのレイアウト・タップでのキャレット配置・入力・キーボードは**動く**。
「素の textarea では全く書けない」ではない。

## 未確認

- IME (変換中の表示、候補ウィンドウの位置)
- 折り返し境目でのキャレット
- 古い Safari / iOS のバージョン差

## 測り方

`test/browser/native.test.ts` と同じ形。`<textarea>` を置いて `userEvent` で本物のキーを打ち、
`selectionStart` を読む。webkit を含めて回せば、この表はそのまま再現できる。
